# 12. Enterprise Role Operating Model (Telegram Bot + Mini App)

## 12.1 Цель раздела

Этот раздел задает единую операционную модель ролей STSphera:

- кто за что отвечает (без дублирования функций),
- кто и когда принимает решения,
- какие действия доступны в Telegram Bot и Mini App,
- какие события запускают уведомления и эскалации,
- что обязательно фиксируется в `AuditLog`.

Документ ориентирован на управляемость, прозрачность и доказательность процессов.

## 12.2 Общая модель

### 12.2.1 Жизненный цикл объекта

| Стадия | Вход | Выход (DoD) | Основной владелец стадии | Контроль | Ключевые артефакты |
|---|---|---|---|---|---|
| 1. Подписание договора | Коммерческое предложение согласовано | Договор подписан, этапы оплат согласованы | Договорной отдел | Генеральный директор (по рискам/лимитам) | Contract, PaymentMilestone |
| 2. Создание объекта | Подписан договор | Создан проект, назначена команда, базовый календарь | Руководитель проекта | Директор направления | Project, UserRole, baseline dates |
| 3. Проектирование | Проект создан | Комплект РД утвержден и выдан в работу | Проектный отдел | Руководитель проекта | Document (versions), remarks |
| 4. Закупка | РД/спецификации утверждены | Заказы размещены, сроки подтверждены | Снабжение | Директор направления | ProcurementOrder, supplier commitments |
| 5. Поставка | Заказы размещены | Материалы/модули доставлены в срок и по качеству | Снабжение | Руководитель проекта | SupplyShipment, acceptance docs |
| 6. Производство | Доступны спецификации и материалы | Модули произведены и готовы к отгрузке | Директор направления / производство | Руководитель проекта | ModulePlanItem status chain |
| 7. Монтаж | Модули/материалы на объекте | Работы выполнены, факт подтвержден, дефекты устранены | Площадка (прорабы), начальник участка | Руководитель проекта | TaskInstance, DailyWorkLog, defect tasks |
| 8. Сдача | Выполнен объем, QC пройден | Акты согласованы и подписаны | ПТО | Руководитель проекта, Директор направления | Acts, closing volumes |
| 9. Закрытие | Все этапы закрыты | Финальный отчет, lessons learned, архив | Руководитель проекта | Генеральный директор | final KPI snapshot, archive package |

### 12.2.2 Модель ответственности (RACI)

| Функция | Инициирует (I) | Исполняет (E) | Контролирует (C) | Принимает (A) | Информируется (N) |
|---|---|---|---|---|---|
| Договор и бюджетный каркас | Договорной отдел | Договорной отдел | Директор направления | Генеральный директор | Руководитель проекта |
| Создание/перезапуск объекта | Руководитель проекта | Руководитель проекта | Директор направления | Директор направления | ГД, смежные отделы |
| Выпуск РД | Проектный отдел | Проектный отдел | Руководитель проекта | Руководитель проекта | Снабжение, площадка, ПТО |
| Закупка/поставка | Снабжение | Снабжение | Руководитель проекта | Директор направления (по критичным) | Начальник участка, прорабы |
| План-факт монтажа | Прораб | Прораб/бригадир | Начальник участка | Руководитель проекта | Директор направления |
| Закрытие объемов/акты | ПТО | ПТО | Руководитель проекта | Директор направления | Договорной отдел, ГД (агрегат) |
| Управление блокерами | Любая роль-владелец задачи | Роль-владелец задачи | Руководитель проекта | Руководитель проекта / выше по эскалации | Все затронутые роли |

### 12.2.3 События, создающие уведомления

Уведомления генерируются только типами триггеров:

- `UI_ACTION` — пользовательское действие (создание, подтверждение, отклонение),
- `DATA_CHANGE` — смена статуса/ответственного/срока,
- `SCHEDULE` — дедлайны и cron-проверки,
- `IMPORT` — загрузка/завершение импортов.

Ключевые event-коды:

- `TASK_ASSIGNED`, `TASK_DEADLINE_T24H`, `TASK_OVERDUE`,
- `FACT_NOT_SUBMITTED`, `FACT_DEVIATION_CRITICAL`,
- `DOC_ON_REVIEW`, `DOC_REJECTED`, `DOC_ISSUED_TO_WORK`,
- `SUPPLY_DELAYED`, `SUPPLY_PARTIAL`,
- `BLOCKER_CREATED`, `BLOCKER_ESCALATED`,
- `ACT_SUBMITTED`, `ACT_APPROVED`, `ACT_REJECTED`.

### 12.2.4 Действия, обязательные для AuditLog

| Категория | Что логируем | Минимальный payload |
|---|---|---|
| Статусы | Любой переход state machine | `entity_type`, `entity_id`, `old_value.status`, `new_value.status`, `actor_id` |
| Сроки | Изменение `planned_start/planned_end` | старое/новое значение, причина, кто согласовал |
| Ответственность | Изменение assignee/reviewer/owner | старый/новый user_id, основание |
| План-факт | Создание/изменение факта, approve/reject | значения plan/fact/deviation, дата, зона |
| Документы | Загрузка версии, ревью, approve/reject, выдача в работу | doc_id, version, reviewer, outcome |
| Финансы/договоры | Подписание, изменение условий, этап оплат | contract_id, milestone, delta |
| Блокеры | Создание, смена критичности, закрытие, эскалация | blocker_type, severity, due_at, escalation_level |
| Системные | Импорт, назначение ролей, RBAC-изменения | source, инициатор, затронутые сущности |

`AuditLog` immutable: только `INSERT`, без `UPDATE/DELETE`.

| Портфельные KPI | Система (read model) | Любая роль руками |

## 12.5 Детализированная ролевая логика

## 12.5.1 Генеральный директор (R-CEO)

1. **Цель**: обеспечить результат портфеля (сроки, бюджет, риск, репутация).  
2. **Метрики успеха**: `% проектов в срок`, `% проектов в бюджете`, `кол-во критических блокеров`, `портфельная маржа`.  
3. **Зона ответственности**: стратегические решения и разблокировка на уровне портфеля.  
4. **Основные действия**: подтверждение антикризисных решений, перераспределение лимитов, запуск управленческой эскалации.  
5. **Критические события**: `OVERDUE_L3`, `BUDGET_DEVIATION_CRITICAL`, `CRITICAL_SUPPLY_DELAY`, `PROJECT_BLOCKED`.  
6. **Telegram Bot (до 6 кнопок)**: `📊 Портфель`, `⚠️ Риски`, `⏳ Просрочки`, `💰 Финансы`, `📈 KPI`, `🚨 Эскалации`.  
7. **Mini App экраны**: Portfolio Dashboard, Risk Heatmap, Delay Funnel, Budget Variance, Critical blockers list.  
8. **Уведомления**: только high/critical; без операционного шума.  
9. **Конфликты/эскалации**: спор DIR vs PM по срокам/ресурсам → решение ГД в течение SLA 24ч.  
10. **Не может**: редактировать задачи, факты, акты, документы.

## 12.5.2 Директор направления (R-DIR)

1. **Цель**: максимизировать маржинальность и пропускную способность направления.  
2. **Метрики**: маржа направления, производительность бригад, выполнение milestone, OTIF поставок.  
3. **Ответственность**: баланс ресурсов между объектами направления, устранение узких мест.  
4. **Действия**: перенос приоритетов, смена owner-ресурса, утверждение критичных переносов.  
5. **Критические события**: множественные просрочки, дефицит ресурсов, рост себестоимости.  
6. **Bot**: `📁 Объекты`, `📊 План-факт`, `📦 Поставка`, `👷 Производительность`, `⚠️ Блокеры`, `🚨 Эскалации`.  
7. **Mini App**: объектный drill-down, ресурсная загрузка, GPR bottleneck, закупка/поставка по объектам.  
8. **Уведомления**: `L2/L3` по срокам, дефициты, отклонение маржи.  
9. **Эскалации**: если PM не закрывает блокер в SLA, DIR принимает решение или поднимает к CEO.  
10. **Не может**: подменять фактические данные площадки и ПТО-первичку.

## 12.5.3 Руководитель проекта (R-PM)

1. **Цель**: выполнить объект в срок, бюджет и качество.  
2. **Метрики**: SPI/CPI, просрочка критического пути, % подтвержденного факта, % закрытых блокеров в SLA.  
3. **Ответственность**: операционный контроль сквозного цикла объекта.  
4. **Действия**: назначение задач, корректировка сроков, согласование документов/актов, управление эскалациями L1.  
5. **Критические события**: невведенный факт, срыв поставки, непройденный ревью РД, просрочка задач.  
6. **Bot**: `📍 Мой объект`, `🗓 График`, `📋 Задачи`, `📦 Поставка`, `📝 Акты`, `🚨 Проблемы`.  
7. **Mini App**: Object Card, GPR dependencies, Task board, Plan/Fact, Subcontractor control, Photo evidence.  
8. **Уведомления**: T-24h, T0, overdue, blocker created/escalated.  
9. **Эскалации**: L1 owner — PM; при >72ч unresolved → DIR.  
10. **Не может**: менять условия договора задним числом; редактировать подписанные акты без перезапуска workflow.

## 12.5.4 Договорной отдел (R-CON)

1. **Цель**: обеспечить юридическую и финансовую корректность обязательств.  
2. **Метрики**: SLA согласования договора/ДС, % просроченных подписаний, точность графика оплат.  
3. **Ответственность**: договоры, допсоглашения, этапы платежей.  
4. **Действия**: создание/обновление карточки договора, запуск согласования, фиксация подписания.  
5. **Критические события**: контракт не подписан к старту, изменены условия, платежный этап просрочен.  
6. **Bot**: `📄 Договоры`, `✍️ На подписании`, `💰 Этапы оплат`, `⚠️ Просрочки`, `📌 Эскалации`.  
7. **Mini App**: Contract Card, approval route, linked project, payment schedule, change log.  
8. **Уведомления**: pending signature, legal rejection, payment milestone risk.  
9. **Эскалации**: юридический блокер >24ч → PM, >72ч → DIR, критично → CEO.  
10. **Не может**: менять производственные статусы и факты СМР.

## 12.5.5 Проектный отдел (R-DES)

1. **Цель**: своевременный и корректный выпуск документации.  
2. **Метрики**: lead time версии, % замечаний закрыто в SLA, % выпусков без rework.  
3. **Ответственность**: версии, замечания, выдача РД в работу.  
4. **Действия**: upload version, resolve remarks, submit for review, issue to work.  
5. **Критические события**: задержка согласования, изменения после выдачи в работу.  
6. **Bot**: `📐 Проекты`, `🔄 На согласовании`, `🧾 Замечания`, `📤 Выдано в работу`, `⚠️ Риски`.  
7. **Mini App**: doc registry, version compare, remarks board, review SLA dashboard.  
8. **Уведомления**: review overdue, critical remark, post-issue change alert.  
9. **Эскалации**: critical doc blocker → PM немедленно; если не снят 24ч → DIR.  
10. **Не может**: подтверждать финансовые этапы и закрывать акты ПТО.

## 12.5.6 Снабжение (R-PRC)

1. **Цель**: поставка нужного объема/качества в срок и в бюджет.  
2. **Метрики**: OTIF, price variance, shortage rate, cycle time согласования счета.  
3. **Ответственность**: закупка, поставка, поставщики, дефициты.  
4. **Действия**: ведение PO, подтверждение отгрузки, фиксация недопоставки/замены.  
5. **Критические события**: срыв срока, изменение цены, недопоставка.  
6. **Bot**: `📦 Закупки`, `🚚 В пути`, `🏗 Дефицит`, `💰 Счета`, `⚠️ Риски`, `📌 Эскалации`.  
7. **Mini App**: supply card, supplier performance, linkage to GPR milestone, ETA confidence.  
8. **Уведомления**: ETA slip, partial delivery, urgent reorder.  
9. **Эскалации**: дефицит критического материала T-24h → PM, T0 → DIR, T+24h → CEO.  
10. **Не может**: изменять факт монтажа и акты ПТО.

## 12.5.7 Площадка (прорабы) (R-FRM)

1. **Цель**: обеспечить ежедневную выработку и достоверный факт.  
2. **Метрики**: daily plan-fact adherence, % своевременного ввода факта, defect repeat rate.  
3. **Ответственность**: исполнение задач на площадке, фотофиксация, оперативные проблемы.  
4. **Действия**: ввод факта, статус задач, создание дефекта/блокера, прикрепление фото.  
5. **Критические события**: отсутствие материалов, аварийный дефект, отклонение > threshold.  
6. **Bot**: `📅 План на завтра`, `📊 Факт за сегодня`, `👷 Люди`, `📸 Фото`, `⚠️ Проблема`, `📋 Мои задачи`.  
7. **Mini App**: daily entry form (zone/axis), task checklist, defect card, media evidence.  
8. **Уведомления**: T-24h, T0, overdue, reminder 19:00/21:00.  
9. **Эскалации**: нерешенный блокер >4ч → SM, >24ч → PM.  
10. **Не может**: утверждать акты, менять договор/РД.

## 12.5.8 Начальник участка (R-SM)

1. **Цель**: синхронизировать бригады и обеспечить выполнение участка в срок.  
2. **Метрики**: productivity index, отклонения по фасадам, % закрытых L1 блокеров.  
3. **Ответственность**: координация нескольких прорабов, баланс людей/фронтов работ.  
4. **Действия**: перераспределение бригад, подтверждение план-факта, контроль просрочек.  
5. **Критические события**: системное отставание фасада, нехватка людей/материалов.  
6. **Bot**: `👥 Бригады`, `📊 Выработка`, `⚠️ Отклонения`, `🧭 Перераспределение`, `🚨 Эскалации`.  
7. **Mini App**: team load board, facade comparison, deviation trend, blocker board.  
8. **Уведомления**: эскалации от FRM, overdue task/fact, supply risks по участку.  
9. **Эскалации**: unresolved >24ч → PM; повторный срыв по зоне → DIR.  
10. **Не может**: менять условия контрактов и утверждать финальные финансовые KPI.

## 12.5.9 ПТО (R-PTO)

1. **Цель**: корректное документальное закрытие объема и актирование.  
2. **Метрики**: cycle time акта, % актов без возврата, разница план-факт к закрытию.  
3. **Ответственность**: исполнительная документация, КС, акты, сопоставление факта.  
4. **Действия**: формирование акта, сверка объемов, запрос подтверждающих доказательств.  
5. **Критические события**: несоответствие объемов, отсутствие доказательств, возврат акта.  
6. **Bot**: `📑 Акты`, `📊 Закрытие объемов`, `🗂 Документы`, `⚠️ Несоответствия`, `📌 На согласовании`.  
7. **Mini App**: act wizard, plan-fact reconciliation, evidence links (photo/doc/zone), approval timeline.  
8. **Уведомления**: акт на согласовании, акт отклонен, недостающие доказательства.  
9. **Эскалации**: акт не согласован >48ч → PM, >96ч → DIR.  
10. **Не может**: назначать бригады и менять производственные приоритеты.

## 12.6 Логика кнопок (универсальные принципы)

### 12.6.1 Telegram Bot

- не более 5-6 кнопок на экран,
- приоритет на действие, а не на аналитику,
- максимум 2 уровня вложенности,
- обязательно callback pattern: `action:entity:id`.

Пример базовых callback:

- `task_accept:{id}`
- `fact_enter:{task_id}:{date}`
- `defect_create:{facade_id}`
- `blocker_raise:{entity}:{id}`
- `open_mini_app:{screen}:{context}`

### 12.6.2 Mini App

- аналитика, детализация, фильтры, графики, зависимости,
- единая схема экранов: `Dashboard -> List -> Card -> Action`,
- правый action-panel: только допустимые RBAC-действия,
- read-only блоки скрывают кнопки изменения (не disabled).

## 12.9 Схема уведомлений и контроль сроков

### 12.9.1 Универсальные SLA-уведомления по дедлайну

| Момент | Условие | Получатель |
|---|---|---|
| T-24h | задача/документ/поставка не завершены | owner + контролер уровня роли |
| T0 | дедлайн наступил, статус не final | owner + PM |
| T+24h | просрочка 1 уровень | PM (L1) |
| T+72h | просрочка 2 уровень | DIR (L2) |
| T+120h или critical | просрочка 3 уровень | CEO (L3) |

### 12.9.2 Эскалация (обязательная модель)

- **L1**: Руководитель проекта  
- **L2**: Директор направления  
- **L3**: Генеральный директор

Эскалация идет только если предыдущий уровень не зафиксировал действие (`ACK`, `REPLAN`, `OWNER_CHANGED`, `BLOCKER_CLOSED`).

## 12.11 План-факт, документооборот, блокеры

### 12.11.1 План-факт (операционный стандарт)

`DRAFT -> SUBMITTED -> REVIEW -> APPROVED`

Обязательные поля для доказательности:

- `task_instance_id`, `date`, `facade/zone/axis`,
- `plan_day`, `fact_day`, `deviation`, `pct_day`,
- минимум одно подтверждение (фото/док/комментарий) для критичных работ,
- `created_by`, `reviewed_by`, timestamps.

### 12.11.2 Документооборот

`DRAFT -> ON_REVIEW -> APPROVED -> ARCHIVED`  
Событие `DOC_ISSUED_TO_WORK` запускает downstream-процессы (закупка/производство/монтаж).

Правила:

- новая версия не затирает старую (immutable version chain),
- после выдачи в работу изменение версии требует события `DOC_CHANGE_AFTER_ISSUE`,
- каждое отклонение документа содержит обязательный reason code.

### 12.11.3 Блокеры

| Тип блокера | Owner по умолчанию | SLA | Эскалация |
|---|---|---|---|
| Договорной | CON | 24ч | PM -> DIR -> CEO |
| Проектный (РД) | DES | 24ч | PM -> DIR -> CEO |
| Поставка/материал | PRC | 12-24ч | PM -> DIR -> CEO |
| Производственный | FRM/SM | 8-24ч | PM -> DIR |
| Акт/документальный | PTO | 24-48ч | PM -> DIR |

Статусы блокера: `OPEN -> IN_PROGRESS -> RESOLVED -> VERIFIED -> CLOSED`.

## 12.12 Схема зависимостей задач (task dependency model)

### 12.12.1 Типы зависимостей

- `FS` (Finish-to-Start) — базовый тип,
- `SS` — параллельный старт,
- `FF` — синхронное завершение,
- `SF` — редкий технический случай.

### 12.12.2 Критический путь объекта (укрупненно)

```
Contract Signed
  -> Project Created
  -> Design Approved
  -> Procurement Confirmed
  -> Supply Delivered
  -> Production Completed
  -> Installation Completed
  -> Acts Approved
  -> Project Closed
```

### 12.12.3 Правила контроллинга зависимостей

1. Задача не может перейти в `IN_PROGRESS`, если ее predecessor в `FS` не завершен.  
2. При сдвиге predecessor система пересчитывает downstream дедлайны и генерирует `TASK_CHAIN_SHIFTED`.  
3. Для критического пути действует усиленный SLA-надзор (T-24h/T0/overdue escalations).  
4. Любая ручная разблокировка зависимости требует reason code и обязательной записи в `AuditLog`.
